# Gym Dashboard — المرحلة الرابعة: عزل البيانات واختبار الضغط

هذا الملف توثيق للاختبار فقط. **لا يُشغَّل اختبار الضغط على الإنتاج ولا على قاعدة بيانات العملاء الحقيقية.**

## التغييرات في هذه الحزمة

1. استعادة مسار بحث الطعام `nutrition.searchFoods` الذي فُقد عند دمج Routes المرحلة الثالثة مع الثانية؛ مع بقاء بحث التمارين.
2. المحافظة على حماية حذف النظام أو اليوم المرتبط من التعديل السابق، والتي سقطت من Controller عند دمج تحسين الأداء.
3. إغلاق مسارات `create/show/edit` للأنظمة التي لا توجد لها إجراءات Controller بدل أخطاء 500 على عناوين غير مستخدمة.
4. حماية بحث الطعام والتمارين بـ 120 طلب/دقيقة لكل حساب؛ والكوتش الذكي بـ 30 طلب/دقيقة لكل حساب. عند التجاوز يرجع HTTP 429. **هذا قيد أمني على معدل الاستدعاء، ولا يعدّل النتائج أو بيانات التمارين/الوجبات.**
5. منع استمرار جلسة حساب عطّله المدير: الجلسة تُلغى، والويب يرجع للدخول أو JSON يرد 403. كان الفحص موجودًا وقت تسجيل الدخول فقط.
6. جعل نتائج بحث التمارين ذات ترويسة `Cache-Control: private, no-store` مثل بحث الطعام.
7. اختبارات لعزل المستخدمين، والروابط، والتعطيل، والحد من المعدل.

## اختبار Laravel قبل أي نشر

من مجلد المشروع، بعد تركيب ملفات الحزمة والحفاظ على أحدث حزم المراحل السابقة:

```powershell
php artisan optimize:clear
php artisan test --filter=TenantIsolationAndRouteAuditTest
php artisan test --filter=InactiveAccountSessionTest
php artisan test --filter=ApiThrottleProtectionTest
php artisan test --filter=FoodCatalogPerformanceTest
php artisan test --filter=TrainingCatalogPerformanceTest
php artisan test
```

لا توجد Migration جديدة ولا عمليات حذف أو تعديل في بيانات المستخدمين. في حال فشل أي اختبار **لا تنشر التعديل** قبل مراجعة التقرير. فحص PHP Syntax وحده ليس بديلًا لاختبارات Laravel.

## قياس الضغط بـ k6 على نسخة تجريبية فقط

حضّر نسخة STAGING **ببيانات وهمية**، وحساب مستخدم مفعل للاختبار، ونسخة من إعدادات الاستضافة. ملف `load-tests/gym-dashboard.k6.js` يتعامل مع نموذج CSRF وتسجيل الدخول والكوكيز تلقائيًا، ويزور صفحات التدريب والتغذية والبحث والقياسات؛ لا يرسل أوامر حذف أو إنشاء متعمدة، لكن فتح `/nutrition` قد يُنشئ وجبات يوم فارغة للمستخدم التجريبي بحسب منطق التطبيق الحالي.

لتثبيت k6 راجع تعليمات النظام في https://grafana.com/docs/k6/latest/set-up/install-k6/ . المثال على Windows PowerShell:

```powershell
$env:BASE_URL="http://127.0.0.1:8000"
$env:TEST_EMAIL="loadtest@example.test"
$env:TEST_PASSWORD="<your-staging-password>"
k6 run .\load-tests\gym-dashboard.k6.js
```

استخدم بيانات دخول **اختبارية** ولا تنشر كلمة المرور أو ملفات `.env` مع التقرير. اختبر تدريجيًا 2 ثم 10 ثم 25 مستخدمًا متزامنًا (VUs) كما في السكربت؛ هذه **أحمال اختبار** وليست سعة مؤكدة للتطبيق. إذا أظهرت النتائج مشاكل، قلل الحمل وراجع الاستعلامات والفهارس والذاكرة والسيرفر قبل توسيع الاختبار.

سجل في التقرير: نوع الاستضافة، PHP workers، RAM/CPU، MySQL، عدد السجلات، حجم البيانات، معدل الطلبات بالثانية، `http_req_duration p95`، معدل الأخطاء، واستهلاك موارد السيرفر. ولتحديد العدد الفعلي للمستخدمين، اختبر على استضافة قريبة من بيئة الإنتاج مع حسابات متنوعة. الطلبات التي تتجاوز حد البحث/الشات قد ترجع 429 وهذا سلوك مقصود لحماية الخدمة؛ افصلها عن أخطاء 500 وأعطال الأداء.

## قبل التشغيل الحقيقي

- تأكد من `APP_DEBUG=false` و`APP_ENV=production` وتفعيل HTTPS على الاستضافة.
- احتفظ بنسخ احتياطية قابلة للاسترجاع، وجرّب الاستعادة دوريًا.
- راقب أخطاء HTTP 500 و429، ووقت SQL البطيء، واستنفاد PHP workers.
- في تعدد السيرفرات استخدم مخزن Rate Limiter مشتركًا (مثل Redis) حتى لا تختلف الحدود من خادم لآخر.
- لا تدّعي قدرة المشروع على استيعاب عدد معين قبل اكتمال اختبار الضغط في بيئته الفعلية.
