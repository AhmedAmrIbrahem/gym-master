# تحسين تأكيد إرسال البروفايدر وتشخيص unknown وثبات الموعد

السجل الأخير أظهر أن Laravel نفّذ المهمة لكن البروفايدر لم يؤكد الإرسال (`provider_unknown`). الفحص وجد ملفات سجل البروفايدر بالحالة unknown أيضًا؛ لذلك ليس هذا منعًا لرسالة ثانية في اليوم. لا تعني unknown بالضرورة أن الرسالة لم تصل: قد تكون وصلت دون رجوع نتيجة مؤكدة من مكتبة واتساب.

## التغييرات

- أصبح طلب `sendMessage` يحدد `waitUntilMsgSent: true` مع استمرار `sendSeen: false`. هذا يطلب انتظار عملية الإرسال من المكتبة بدل الاعتماد على رجوع فوري. لا نصنف رجوعًا فارغًا على أنه نجاح، ولا نكرر الإرسال عند نتيجة غير مؤكدة.
- البروفايدر يطبع سطرًا آمنًا يبدأ بـ`[gym-whatsapp]` عند الفشل، يبين مرحلة العمل وسببًا مختصرًا وكود خطأ إن وجد. لا يطبع raw error أو رقم المستلم أو نص الرسالة أو QR أو مفاتيح الخدمة. تتضمن المراحل قراءة سجل منع التكرار، فحص المستلم، حجز المفتاح، إرسال واتساب، وحفظ النتيجة.
- Laravel يسجل نوع خطأ الاتصال أو كود HTTP وحالة البروفايدر المسموحة فقط، دون الأسرار أو أجسام الطلبات أو الردود الخام.
- وقت الموعد تغيّر في ناتج التشخيص إلى لحظة تنفيذ المهمة، بينما المهمة لا تعدله في الكود. هذا يرجّح تفعيل تحديث ضمني تلقائي لعمود TIMESTAMP في MySQL/MariaDB. يغيّر migration جديد العمود `scheduled_at` إلى DATETIME بدون تحديث تلقائي، مع استمرار حفظه UTC بواسطة UtcDateTime. تم تعديل migration إنشاء الجدول أيضًا للتثبيت الجديد. هذا إصلاح مستقل لثبات التاريخ، وليس دليلًا على سبب فشل تأكيد مكتبة واتساب.
- لا نحاول إصلاح أو إعادة إرسال سجلات unknown القديمة تلقائيًا، ولا نمسح ledger أو جلسة الحساب. تغيير وقت قديم بالفعل لا يُستنتج بأثر رجعي ولا يُعاد بناؤه تخمينيًا.

## التركيب فوق نسختك الحالية

1. أوقف queue:work وschedule:work مؤقتًا، وأوقف البروفايدر بـCtrl+C من نافذة npm start لإعادة تحميل كوده بعد النسخ.
2. فك ملفات الحزمة داخل جذر مشروع Laravel، ووافق على استبدال الموجود مع الحفاظ على المسارات.
3. نفّذ من جذر المشروع:

```powershell
php artisan migrate
php artisan optimize:clear
```

لا تستخدم migrate:fresh أو queue:retry all، ولا تعدّل unknown إلى pending.

4. من مجلد `services/whatsapp-provider` شغّل:

```powershell
npm start
```

لا توجد مكتبات جديدة ولا حاجة إلى npm install. الجلسة المحفوظة تبقى كما هي. تأكد من «متصل وجاهز» في صفحة السوبر أدمن.

5. من جذر Laravel شغّل عامل الطابور في نافذة مستقلة:

```powershell
php artisan queue:work --queue=gym-reminders --tries=1 --timeout=60 --sleep=2 -v
```

وفي نافذة أخرى:

```powershell
php artisan schedule:work
```

6. اختر موعدًا جديدًا لليوم الحالي بعد ثلاث دقائق، وحدد الموافقة ثم احفظ. راقب وصول رسالة واحدة. إذا لم تصل، أرسل فقط السطر الجديد الذي يبدأ بـ`[gym-whatsapp]` من نافذة npm start، ونتيجة سجل الإرسال الجديد. لا ترسل ملفات .env أو بيانات الجلسة.

بعد تشغيل migration يمكن التأكد من نوع العمود في أداة قاعدة البيانات: يجب أن يكون DATETIME وألا يحتوي `ON UPDATE CURRENT_TIMESTAMP`. تغيير النوع يحافظ على القيم الحالية؛ لا يعيد الزمن الصحيح لسجلات كان عمودها قد تغير سابقًا. الرجوع عن migration يحتفظ عمدًا بـDATETIME ولا يعيد السلوك الضار أو يحذف التاريخ.

## التحقق والحدود

اختبارات Node تغطي طلب انتظار التأكيد، والرجوع الفارغ كـunknown دون إعادة إرسال، وخصوصية سجل الأخطاء، ومنع التكرار، وحفظ السجل بعد إعادة التشغيل. اختبارات Laravel تغطي مسار HTTP وجدولة الأيام والرسائل والصلاحيات، وثبات scheduled_at عند تحديث حالة المهمة.

النتائج: نجح 159 اختبار Laravel و809 assertions، ونجح 23 اختبار Node. اختبار loopback HTTP واحد تم تخطيه بسبب رفض الشبكة المحلية في بيئة الفحص؛ معالج HTTP نفسه اختُبر دون sockets.

لم يُختبر إرسال واتساب حقيقي من بيئة الفحص، ولم يتوفر اتصال MySQL حي فيها للتحقق من metadata العمود. التشغيل السابق اختُبر بقاعدة SQLite معزولة. لن يحوّل هذا التحديث كل عطل محتمل في WhatsApp Web إلى إرسال ناجح؛ إذا استمرت المشكلة يعطي سطر التشخيص مرحلة محددة للخطوة التالية.

يوجد بلاغ في مستودع المكتبة عن [رجوع sendMessage بقيمة undefined في 1.34.7](https://github.com/wwebjs/whatsapp-web.js/issues/201857)، وتوثيق [Client API](https://docs.wwebjs.dev/Client.html) يوضح خيار انتظار الإرسال. هذه قرينة على احتمال قصور النتيجة وليست إثباتًا أن جهازك يواجه نفس السبب. لم نعدّل node_modules أو نجلب نسخة Git غير مختبرة.
